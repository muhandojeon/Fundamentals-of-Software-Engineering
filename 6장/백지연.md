# 6장 낯선 시스템에 빨리 친숙해지기

프로젝트의 큰 그림이나 목표를 이해하는 기술을 알아보자.

## 낯선 코드 이해

### 프로젝트 이해

**코드보다도 프로젝트의 목적과 이해부터 파악해야 한다.**  
프로젝트의 존재 이유, 이해관계자, 회사에서 이 프로젝트가 갖는 의미, 사업에서 큰 비중을 차지하는지.. → **제품에 대해 깊이 아는 사람부터 찾아가자**

찾아갈 순서
1. 제품 책임자 - 개요 파악
2. SW 엔지니어 - 기술적인 측면 살펴보기, 당시 내려진 결정에 대한 통찰 얻기
3. 고객 - 사용자 유형, 목표, 고충을 알면 기술적 결정이 내려진 맥락을 이해할 수 있음

### 기존 문서 검토

ADR, 온보딩 문서 읽기 → 문서 보완하고 팀에 기여하기

> 앞으로는 아키텍처 결정 회의에서 AI로 회의록 생성하고, 회의록 기반으로 [ADR 템플릿/예시](https://github.com/architecture-decision-record/architecture-decision-record) 참고해서 ADR 문서 작성하라고 하면 되겠네요

> 요즘에는 온보딩을 어떤 방식으로 하고 계신가요?

문서는 거짓말을 할 수 있지만 코드는 절대 거짓말을 하지 않는다 = 읽은 내용을 실제로 돌아가는 코드와 대조해서 확인하자

> 코드는 계속 변하는데 GitHub 이슈는 잘 관리되지 않는 것 같아서 AI 시켜서 코드랑 대조한 뒤 해결된 이슈는 close하고 있습니다  
> PR 올리고 나서 추가 커밋하면 PR 본문 갱신하라고 시키는 것도 요즘 많이 하는 것 같네요

### 아키텍처와 프로젝트 구조 이해

프로젝트 구조는 많은 정보를 드러내며, 코드를 탐색할 때 도움이 되는 전체적인 시야를 제공한다.

> 책에는 백엔드 중심으로 작성되어 있는데 프론트엔드는 FSD가 여기에 해당하려나요

### 실행 흐름 파악

이제 코드를 볼 차례

애플리케이션 진입점 찾기, 요청과 응답 추적하기, 외부 의존 관계 파악, 내부 프레임워크와 라이브러리 파악 → 실행 흐름 이해

### 점진적인 멘탈 모델 구축

멘탈 모델 = 시스템이 작동하는 방식에 대한 우리 머릿속에 표현된 그림

AI한테 머메이드 구문 생성해 달라고 요청하는 것도 하나의 방법

점진적으로 시야를 넓혀가자

## 안전한 수정

- 리팩터링 전에 테스트를 추가하라
- 스카우트 규칙: 파일을 손볼 일이 있을 때마다 코드 품질을 점진적으로 개선
    - 누락된 문서 추가
    - 변수/메서드 이름 개선
    - 복잡한 메서드 분해
    - 데드 코드 제거
    - 발견한 사소한 버그 수정

| 리팩터링 적합 | 리팩터링 부적합 |
| :-: | :-: |
| 작업 중인 코드를 이해하기 어렵다 | 코드가 잘 작동하며 수정할 일이 거의 없다 |
| 해당 영역에 기능을 추가해야 한다 | 마감 기한 압박이 심하다 |
| 코드의 버그를 수정하고 있다 | 코드를 깨뜨릴 위험이 이득보다 크다 |
| 코드가 성능 문제를 일으키고 있다 | 현재 작업 범위를 넘어서는 광범위한 변경이 필요하다 |
| 여러 개발자가 이 영역에서 자주 작업한다 | 안전을 보장하는 테스트가 없다 |

> 요즘에는 AI가 있으니까 예전만큼 리팩터링이 막막하게 느껴지지 않아서 좋아요

> 낯선 코드를 이해하는 데 가장 도움이 되는 건 결국 직접 기능을 만들어 보는 것 같아요
