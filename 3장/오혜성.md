# 사람을 위한 코드 작성법

- 결국 코드는 사람이 읽도록 작성되어야 한다
> 사람이 읽기 좋은 코드가, 에이전트도 읽기 좋은가?
> 하드웨어가, 전력 소비가, 월등히 발전한다면 기계어가 제일 좋은 기술 아닐까?라는 망상..

## 바퀴 재발명 금지

- 용감하게 왜? 라고 물으며 타성에 도전해라
  - 찾아낸 패턴이나 방식을 무심코 따르거나 이유를 충분히 이해하지 못한 채 AI가 생성한 코드에 안주하게 될 수도 있다

## 좋은 코드란

- 사람들이 관찰받을 때 행동을 수정한다는 호손 효과로 좋은 효과를 얻을 수 있다 

> 에러률

## 간결함의 가치

- 소프트웨어 엔지니어들이 옹호하는 코드를 길들이는 기법 대부분이 컴퓨터 과학의 제0법칙인 높은 응집도와 낮은 결합도로 귀결된다

### 상속보다는 구성

- 상속을 재사용 기법으로 사용하지만 재사용은 부수적인 결과일 뿐, 목적이 아니다.
  
### 짧은 메서드 지향

- 메서드 이름에 접속사(and, or, but)가 포함되어 있다면 해당 메서드가 너무 많은 일을 하고 있다는 신호다. 메서드 이름은 명확하고 간결해야 하며 기교를 부려서는 안된다.

## 독자를 위한 코드 작성

- 코드를 신문 기사처럼 '역피라미드' 방식으로 작성할 수 있다
> '뉴스페이퍼 패턴으로'를 ai에게 먹여두면 알잘딱 알아듣고 좋더라구요


## 코드 주석의 문제

- 고고학적 여정에서 흥미로운 경유지가 될 수는 있지만, 추적 번호, 날짜, 이름, 변경 내용이 반복되면 노이즈를 더할 뿐이다. 소스코드 관리 도구가 담당하게 해라
> ai가 지라 티켓이라던지, PR 번호라던지.. 를 주석에 싸버리는 경우가 많아서 관례를 정해두니 좋더라구요


## 코드 리뷰

- 무언가를 훌륭하게 만드는 유일한 방법은 그것이 아직 훌륭하지 않을 수 있다는 점을 인정하는 것이다. 목표는 최선의 해결책을 찾는 것이지 그것으로 개인의 자기 가치를 가늠하는 것이 아니다.
