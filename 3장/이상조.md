## 바퀴 재발명 금지
ai한테 작업 시켜놓으면 동일한 역할을 하는 함수를 중복 생성하는 경우도 있고, 전혀 다른 역할을 하는 함수를 억지로 뜯어고쳐 공용함수로 승격시키는 경우도 있고, 특정 함수를 약간 수정하면 공용함수로 승격시킬 수 있을 것 같은데 캐치하지 못하는 경우도 있고 다양하다. 어느정도는 개발자의 감에 의존해야하는 작업이라고 생각하는데, ai가 이걸 어떻게 해줄 수 있을지 모르겠네

## 독자를 위한 코드 작성
a프로젝트에 있던 코드를 b프로젝트에 옮겨야 할 일이 있었는데, 로깅 관련된 코드는 옮기지 않기로 했었다. 근데 뭘 누르거나 화면에 보일때마다 ~~/events, ~~/impressions 라는 api를 호출하는 부분이 있더라. 왜 로깅을 별도의 로깅 레이어에서 처리하지 않고 직접 호출하지? 라고 생각해면서 다 지웠는데, 알고보니 머신러닝 모델을 위한 별도 api였다.
이걸 되살리면서 네이밍의 중요성을 다시 느꼈달까...

## 코드 변경 이력 주석
모 인터넷뱅크 홈페이지 드가서 개발자도구 열어서 소스코드 보면 거기 누가 수정 언제했는지 주석으로 다 남아있음 ㅋㅋ 아직도 그대로일려나
나는 원래 코드를 잘짜면 주석이 필요없다고 생각했었는데, 증권 도메인을 접하면서 생각이 많이 바뀌었다. 이런게 왜 필요한거고 어디서 쓰일거고 때로는 정말 이해가 안가는 동작이 있다면 그건 대부분 도메인 이슈거나 뭐... 그래서 주석을 꼼꼼하게 남겨놓고 관련 문서나 슬랙 스레드 링크를 남기는 것도 중요하다고 생각하게 되었음.

## 형식적 코드 리뷰 금지
나는 코드리뷰 할때 내 리뷰가 크게 의미가 있을까? 라는 생각을 종종 한다. 뭔가 설계적인 측면을 짚어내기에는 내가 이 작업에 대해 배경지식이 없고 처음부터 같이 설계에 참여한 것도 아니다보니 중간중간 코드의 파편만 봐서는 그저 문법, 리액트 동작, 틀린그림찾기 같은 느낌의 리뷰만 할 수 있을 뿐임. 사실 무슨무슨 역할을 하는 함수를 만든다. 어떻게 생긴 컴포넌트를 만든다 이런건 대부분 약간약간의 취향 차이만 있을 뿐이지 사람마다 크게 달라질건 없다고 생각한다. 근데 그것들이 결국 왜 필요하고, 어떤 방식으로 얽혀서 커다란 기능을 굴러가게 할지 설계하는 것은 코드 작성자의 머리 속에나 있는 것인데 그 맥락 없이 양질의 리뷰가 가능할까?
ai이전에도 그랬지만, ai로 인해 코드 생산 속도가 빨라지면서 더 심해지는 것 같다.
