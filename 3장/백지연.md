# 3장 사람을 위한 코드 작성법

AI의 등장으로 직접 개발은 줄어들고, AI가 생성한 코드를 수정하고, 교정하고, 검토하는 방향으로 소프트웨어 엔지니어의 직무가 변하고 있다.  
**하지만 코드를 잘 검토하려면 코드를 잘 작성할 수 있어야 한다. 결국 코드는 사람이 읽도록 작성되어야 한다.**

새로운 코드르 작성하기 전에 몇 가지 질문을 스스로 던져보는 것이 도움이 된다.
- 현재 코드 어딘가에 이미 구현되어 있는가
- 프로젝트에서 이미 사용하는 라이브러리 중 이 문제를 해결하는 것이 있는가
- 이 문제를 해결하는 오픈소스 라이브러리가 있는가
- 프로그래밍 언어에 이미 기능이 있는가

**가져다 쓸 수 있으면 활용하고, 그렇지 않다면 코드를 작성하며 테스트를 작성하자.**

좋은 코드를 정의하기는 어렵지만 보면 알 수 있다.  
시간이 지나면 서서히 감각이 생기고, 코드 스멜을 말할 수도 있게 된다.

**지표는 전체 코드에 대한 통찰을 제공할 수 있다.**  
소나큐브, JS힌트 같은 소스 코드 분석기를 쓰면 특정 유형의 버그와 안 좋은 코딩 관행을 방지하는 데 도움이 된다.  
아직 없다면 프로젝트에 도입하는 작업을 주도해 보는 것도 좋다.

> 코드 스멜 제거할 때 소나큐브 MCP 잘 쓰고 있습니다

사람들이 관찰받을 때 행동을 수정한다는 호손 효과(고속도로에서 경찰을 보고 모두가 속도를 줄이는 것과 같다)로 좋은 효과를 얻을 수 있다.  
ex. 테스트 비율을 높이고 싶다면 code coverage를 눈에 띄게 게시하기

코드를 길들이는 기법 대부분이 **높은 응집도와 낮은 결합도**로 귀결된다.
- 응집도 : 사물들이 어떻게 관련되어 있는지를 나타내는 척도
  - 높은 응집도 = 본질적으로 비슷한 것들이 모여 있는 것
- 결합도 : 모듈이나 루틴이 서로 의존하는 정도
  - 높은 결합도 = 코드의 한 부분을 변경했을 때 관련 없어 보이는 시스템의 다른 부분에 예기치 않은 영향을 미침 = 수정하기 어려움

메서드는 오직 한 가지 일만 해야 하며, 그 일을 잘 수행하고 더 큰 목표를 달성하기 위해 협력해야 한다.  
메서드 이름에 접속사(and, or, not)가 포함되거나 이름을 짓기 어렵다면 해당 메서드가 많은 일을 하고 있다는 신호다.

코드 주석은 코드와 같은 내용의 글을 작성하는 것이기에 DRY 원칙을 위반한다.  
코드를 수정할 때 주석은 수정되지 않을 수도 있기 때문에 유지보수의 골칫거리도 될 수 있다.  
만약 상황 설명이 필요하다면 무엇을 했는지가 아니라 왜 했는지에 초점을 맞춰야 한다.  
주석보다 테스트를 작성하자.

소프트웨어는 어렵고, 우리가 일하는 도메인은 복잡하다.
- 본질적 복잡성 : 비즈니스 규칙의 미묘한 차이부터 팀과의 소통, 끊임없이 변화하는 코드의 특성에 이르기까지 소프트웨어에 내재된 것
  - 이 복잡성을 감수하는 대가로 우리가 급여를 받는 것이고, 제거할 수 없다.
- 부수적 복잡성 : 요란한 기술부터 과도한 도구에 이르기까지 개발자가 필요 이상으로 일을 어렵게 만드는 것
  - 이걸 경계해야 한다. 단순하게 유지하자.
 
> 복잡성을 감수하는 대가로 급여를 받는다는 부분이 공감되네요
