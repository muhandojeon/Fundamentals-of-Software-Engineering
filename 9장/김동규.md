# 9장 소프트웨어 아키텍처: 복잡하고 중요한 결정

개인적으로 아키텍처란 우리의 환경에 맞춰 가장 좋은 서비스 환경을 만드는 것이라고 정의했다.

## 득실 관계

좋은 것도 나쁜 것도 없다.
- 아키텍처를 고민할 때 1차적으로 대중적으로 요즘 많이 사용하는 것들을 확인한다 (유행하는 것 X).
- 해당 아키텍처가 우리 상황에 맞을지 판단하고, 약간씩 커스텀해서 사용한다.
  - 회사들의 작업 환경을 까보면 같은 React 기반 프로젝트라도 목적과 환경에 따라 매우 다르다.

대중적인 아키텍처를 따라가면 반은 하는 것 같다.

## 품질 속성

이해관계자에게 중요성을 이해시키는 것이 중요하다고 한다. 내용에는 모두 공감하지만, 개발 담당자로서 해당 소프트웨어 프로젝트의 중요도와 결과가 어느 정도 비중인지 스스로 판단하는 것도 매우 중요하다고 생각한다 (비즈니스적 관점).
- 중요하지 않은 프로젝트에 열과 성을 다해 훌륭한 소프트웨어 스킬이나 아키텍처를 적용한다면 약간 손해라고 생각한다.
- 개인적으로 중요하지 않은 프로젝트는 생산성 위주로 세팅한다 (익숙한 것, 제일 쉽게 구현하는 방법).

## 애자일 아키텍트

오우 ㄷㄷ... 초기 스타트업에서는 이런 식으로 많이 하는 것 같다. 이 프로젝트가 언제까지 유지될지 모른다 (내일이라도 사라질 수 있음).

## 아키텍처 결정 기록

신규 서버를 올리기 위해서는 내부적으로 CTO 승인을 받아야 해서 비슷한 문서를 정리하긴 한다. 승인용이며 기록은 지속적으로 관리되지는 않는 것 같다 ㅎㅎ...
- TPS, K8s 사용 Pod 수, 인프라에 올라간 유저 엔드포인트 간 통신 등의 인프라 아키텍처, 사용 메모리·CPU 예상치, 모니터링 링크 등이 문서에 포함된다.
