# 아키텍처란 무엇인가
프론트엔드에서 아키텍처란 뭘까? 책에서는 설계로 인해 산출물의 성능이나 확장성, 유지보수성이 결정되는 무언가로 보인다. 마이크로 프론트엔드처럼 멋진 것도 있겠지만, 대부분 적당한 크기의 프론트엔드 앱은 뭐.... 폴더구조 정도가 아닐까?

# 득실 관계
사실 항상 확장을 염두에 두고 첫 삽을 뜨는게 무조건 이득이지 않나?(리소스만 충분하다면) 다만 리소스가 충분치 않아서 어딘가 타협점을 찾게 되는 것 같다. 하지만 이젠 AI를 쓰면 리소스를 극단적으로 줄일 수 있으니 더 변경에 용이하고, 더 유지보수하기 용이한 형태로 개발이 가능해진게 아닐까?
근데 책에서 나온 예시가 브라질 서비스를 만들면서 다른 나라까지 고민하고 뭐 이런건데 따지면 한도 끝도 없지 않나? 다른 나라, 다른 행성은 그럼? 다른 우주? 다른 차원?? 어디까지 갈건데...
우리가 눈에 보이는 곳 까지 확장한다고 해서 그게 확장성을 염두에 둔걸까? 다른 나라에서도 원활하게 돌아가도록 정책을 분리하고 어쩌고... 다 해놨는데 스페이스X가 진짜 인류를 화성으로 데려가서 화성의 개발환경까지 고려해야한다면?
그럼 화성 환경은 우리가 아직 구축도 안했는데 그걸 예측해서 거기에 맞는 확장성을 지금 고려할 수 있나?
결국 우리는 지금까지 쌓아온 수많은 사례에서 '이렇게 짜면 확장성이 높음'이라는 일반적 사실을 끌어내서 개발하고 있는데, 뭔가 페러다임을 깨는 외부 요인이 발생하면 지금까지의 확장성이라는 것도 별 의미없는 요소가 될지도 모르겠다.

# 아키텍처와 설계
최근 아예 제로베이스에서 새로운 앱을 개발하고 있는데, 단기간에 개발해야해서 프론트 개발자 4명이 각자 전략적 결정을 내리면서 개발하고 있다.
약간 스트릿 농구와 엘리트 농구의 차이 같은 느낌? 개인의 기량에 의존 + 가능한 팀원의 결정을 신뢰하다 보니 일단 자유로워서 좋긴 함.
단점은 서비스 전반에 영향을 줄 수 있는 문제가 생겼을 때, 이 맥락을 개인 플레이 하고 있던 사람들에게 다 전파하고 100% 이해시키고 같이 고민하기가 어렵다보니 이런 문제 조차도 한두명의 판단에 맡겨야 한다는 점?

근데 최근엔 AI가 너무 잘해주다보니 전술적인 결정 역시 큰 숙고 없이 내리게 되는 것 같다.
예를 들어 우리 앱은 필요한 사내 라이브러리가 있는데 정책이 달라서 살짝만 수정해야한다면 그냥 그대~~~로 프로젝트 내에 복붙해온다.
별 고민이 필요없다. 나중에 원본 라이브러리를 수정해서 반영할 수도 있고 아예 새로운 라이브러리를 만들어야 할 수도 있고 어떻게 될지는 모르겠지만 당장 필요한 것들 통째로 다 옮겨와서 개발하고 정리는 AI한테 딸깍으로 맡겨버림.
FSD로 작성된 기능을 옮겨올때도 FSD 사용하지 말고 파일 역할별 폴더링하라고 시키니깐 아주 깔끔하게 옮겨와주고...
네이티브 코드를 리액트로 포팅해오는 것도 그냥 딸깍이고...
아니 이정도로 딸깍으로 다 되는데 설계라는게 큰 의미가 있나 싶기도 하다. 설계가 잘못됐어? 그걸 알 필요 있나? 어차피 우린 뭘 하고싶은지만 말하면 설계를 뜯어고치든 뭘 어떻게 하든 구현은 AI가 다 해주는데
라는 책임감 없는 말은 하지 말길 바란다...
